# V1 — HISTORICAL / compatibilidad

## Estado

```text
language_version = 1.0.0
source_profile    = bounded_v1
status            = historical
```

V1 es una generación histórica del lenguaje, pero varias de sus estructuras siguen presentes como **compatibilidad**: linked program, pipelines de lowering, Program IR V2/V3, runtime V3, checkpoints y Python host V1.

No es la ruta recomendada para escribir un programa nuevo Total-Core.

## Qué aportó

V1 consolidó una fuente acotada, linking/proyecto explícito, lowering content-addressed y una separación fuerte entre build y runtime portable.

La autoridad de source V1 es `spec/TEV_SCRIPT_V1_SEMANTIC_CONTRACT.md` y la referencia histórica `docs/TEV_SCRIPT_V1_LANGUAGE_REFERENCE.md`.

## Linked Program

La matriz mantiene:

```text
linked_program version 1 / profile v1 / compatible
```

con autoridad `spec/TEV_SCRIPT_V1_CANONICAL_LINKED_PROGRAM.md`.

Esto importa porque un proyecto V1 cerrado no se convierte automáticamente en un `unit` Total-Core. Puede existir como artefacto histórico/compatible con su pipeline.

## Program IR

La línea V1 conserva Program IR V2/V3 en la matriz:

- IR V2: histórico `portable_legacy`;
- IR V3: compatible `portable`.

La API pública current aún exporta helpers de compile/lowering/validate/runtime para esta compatibilidad.

## Python host V1

`PythonRuntimeHostV1` ejecuta IR V3 precompilado con least-authority capability bindings. No es el runtime Total-Core V5; es una integración compatible que conserva su contrato.

## Qué NO hacer

- no cambies un header V1 a 3.1 para «migrar»;
- no pases IR V3 al validator V5 Total-Core;
- no borres receipts históricos porque exista una versión más nueva;
- no presentes APIs V1 como la ruta current para nuevos usuarios.

## Migración conceptual

Si quieres reutilizar lógica antigua en el mundo current, identifica primero qué artefacto/semántica tienes. La migración correcta puede ser portar source a V2/V4, mantener un adapter de compatibilidad o crear una frontera explícita; nunca renumerar el JSON.
