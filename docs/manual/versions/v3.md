# V3 — HISTORICAL en navegación, semantic-process compatible

## Estado

```text
language_version = 3.0.0
source_profile    = semantic_process
status            = compatible
Program IR        = V5 semantic_process
```

V3 introdujo el semantic-process de facts, Field, Transformations y labels acotadas. Total-Core 3.1 reutiliza esta base, por lo que V3 es histórico como ruta principal pero **compat** como contrato precedente.

## Header

```text
process Demo version "3.0.0";
```

## Superficie

```text
authority
quantum_steps
fact
field
transform
label apply
label branch_fact
label jump
label halt
entry
```

Los ciclos están permitidos porque el runtime usa quanta finitos y continuations.

## Program IR V5 Semantic Process

Identidad:

```text
TEV_SCRIPT_PROGRAM_IR_V5_SEMANTIC_PROCESS_V1
language_version = 3.0.0
profile = semantic_process
```

Sigue siendo un artefacto distinto del V5 Total-Core 3.1.

## Relación con 3.1

El frontend 3.1 delega la base semantic-process al parser/compiler V3 y añade:

```text
unit ... profile ...
invoke_v4 ...
```

La delegación evita duplicar semántica, pero no convierte un source V3 en source 3.1 automáticamente: el header/version y la identidad siguen separados.

## Compatibilidad

Los artefactos V3 publicados/compatibles deben seguir validándose por su schema/profile propio. Un V3 no se admite como Total-Core cambiando `profile` en JSON.

## Qué NO hacer

- no documentar `unit` como keyword V3;
- no usar `invoke_v4` en un source 3.0 salvo que otro perfil futuro lo defina;
- no pasar Program IR V5 Semantic Process al runtime Total-Core como si fuera root current;
- no eliminar tests V3 porque 3.1 delega en ellos.
